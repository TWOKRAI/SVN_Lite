# Исследование: доступ ИИ-агентов к функциям SVN-lite через CLI и MCP

Статус: только исследование. Код программы, тесты и README не менялись. Версия программы 1.2.9, дата 2026-11-02.
Проверено чтением кода и `grep`; тесты не запускались, живой сервер и собранный exe не проверялись. На машине разработки
`python 3.11.4`, `svn` из VisualSVN в PATH, пакета `mcp` нет (`pip list`).

## 0. Вывод

Возможно, сложность средняя. Ядро (`svn_core`, `config`, `notifier`, `publish`, `templates`, `localrepo`, `importer`,
`server`, `messages`, `checks`, `projectmeta`, `mirrors`, `audit`) tkinter не импортирует (проверено `grep`), поэтому
read-only CLI (проекты, состояние, что изменено, что нового, история, занятые файлы) собирается почти без правок GUI.
Основная работа не в самой команде, а в трёх вещах:

1. Оркестрация зашита в замыкания GUI (повтор сохранения после «на сервере новее», cleanup при блокировке копии, отсев мусора
   после «Получить новое», цикл занятия файлов, создание проекта из шаблона). Нужно вынести примерно 650 строк
   из ~11 000 строк GUI (раздел 1).
2. Второй процесс рядом с окном. Реестр занятых папок `publish._busy` живёт в памяти, журналы задач `create_jobs/*.json` без pid,
   `SettingsStore.save` затирает файл целиком, журнал `svn_helper.log` с ротацией. Всё это ломается при двух процессах
   (раздел 5). Для мутирующих команд нужен межпроцессный замок и правка разбора журналов.
3. Безопасность: агент не должен получать пароль и делать необратимое без человека (раздел 3.3).

Рекомендуемый первый этап: read-only консольный `svnlite.exe` (без mcp) + пользовательский skill для Claude Code.
Около 500 строк, GUI не меняется, польза сразу. MCP строить вторым шагом как тонкий адаптер над теми же функциями.

## 1. Что уже можно вызывать из CLI/MCP

`import svnhelper.svn_core` и остальные модули ядра tkinter не тянут. Исключение: всё из `svnhelper.gui.*`, потому что
`svnhelper/gui/__init__.py` импортирует `app` (tkinter). Даже чистые `gui/models.py` (`MineItem`) и `main_action`
из `projects_tab.py` из CLI не импортировать. Начальная сборка контекста (`app.main`, строки 1528-1536: `SettingsStore`,
`load_shared_cache`, `build_config`, `find_svn`, `SvnClient`, `effective_credentials`) состоит из 6 вызовов, её нужно вынести в
`svnhelper/context.py`.

| Функция | Где в коде | Готовность к вызову из CLI | Сложность |
|---|---|---|---|
| Контекст (конфиг, svn.exe, клиент) | `gui/app.py:main` 1528-1536 | вынести 6 строк в `context.make_context()` | S |
| Найти скачанные проекты | `notifier.discover_projects(dirs)` | готово (подпапки с `.svn`, без точечных) | S |
| Тип папки (обычная / проект / повреждена / локальная история) и линия (основная, ветка, версия) | `projects_tab._probe_item` + `gui/models.MineItem` | в GUI-модулях; вынести в `projects.py` (~100 строк) | S |
| Состояние проекта (правки, новое, конфликт, занятые) | `SvnClient.status(path, check_server, rules)`, `notifier.check_project` | готово | S |
| Человеческий статус | `messages.status_line` | готово, но подсказка ссылается на кнопки окна («Нажмите «⟳»»): для CLI брать только текст и заводить свой `next_step` | S |
| Что изменено у меня | `WcStatus.local_changes` (путь, вид, `needs_lock`, `locked_by_me`) | готово | S |
| Что нового на сервере | `status(check_server=True).incoming_files`, `SvnClient.incoming_log` (кто, когда, комментарий, файлы) | готово | S |
| История | `SvnClient.recent_log(path, limit)` | готово | S |
| Занятые файлы | `WcStatus.my_locks/other_locks`, `SvnClient.locks_under(url)`, `remote_lock` | готово | S |
| Проверка связи | `SvnClient.has_connection`, `Settings`/`config.find_svn` | готово | S |
| Список шаблонов | `templates.load_templates` (кэш, офлайн-режим) | готово | S |
| Ветки и версии | `list_lines`, `branch_history`, `diff_summary`, `copy_url` | готово (в первый этап не брать) | S |
| Получить новое | `SvnClient.update`; логика `E155004 -> cleanup -> повтор`, отсев мусора `audit.junk_among` + `exclude_paths`, `cleanup` после отмены/BUSY лежит в замыкании `_start_update.work` (~35 строк) | вынести в `ops.update_project` | S-M |
| Сохранить на сервер | `SvnClient.commit` (add/rm, файл комментария UTF-8, `LOCK_REQUIRED` до действий); повторы «`OUT_OF_DATE` -> update -> commit» и «`LOCK_REQUIRED` -> lock -> commit» в `_run_commit/_commit_failed` (~45 строк) | ядро готово; для агента повторы не нужны, возвращать ошибку и дать флаги; вынести `ops.save_project` | M |
| Занять / освободить | `SvnClient.lock/unlock/remote_lock`; цикл по файлам и разбор `LOCKED` в `_run_locks.work` (~20 строк) | вынести в `ops.lock_files/unlock_files` | S |
| Разобрать конфликт | `SvnClient.resolve(path, accept)` | готово, но выбор «моя/серверная» решает человек (потеря данных); агенту не давать | - |
| Починить папку | `SvnClient.cleanup` | готово, но опасно параллельно с окном (раздел 5); агенту не давать | - |
| Создать проект из шаблона (локально или на сервер) | `templates.fetch_template/build_plan/apply_plan`, `projectmeta`, `localrepo.create_local_repo`, `importer.create_project`; сборка, журнал, откат: `create_local_project`, `create_server_project`, `download_project`, `check_base_dir`, `load_template` в `gui/new_project_dialog.py` строки ~75-525 (модуль импортирует tkinter) | перенести ~450 строк в `newproject.py`, в старом модуле оставить реэкспорт (тесты патчат `svnhelper.gui.new_project_dialog.*`) | M |
| Отправить на сервер («Отправить позже») | `publish.check_publish/publish/resume_publish`, журнал, `recover_job` | готово (без tkinter) | S для вызова, риск высокий |
| Сохранить у себя (локальная история) | `localrepo.save` | готово | S |
| Занятые папки | `publish.is_busy/busy_paths/mark_busy` | реестр в памяти процесса: для CLI/MCP недостаточно | M (раздел 3.4) |
| Уведомления, трей, автозапуск, тема, окна | `notify_ui`, `popup`, `tray`, `autostart`, `theme` | CLI не нужны, не трогать | - |

Итог по выносу: `context.py` ~30 строк, `projects.py` ~120, `ops.py` ~150, `newproject.py` ~450 (перенос), остальное
в GUI превращается в вызовы. Ориентир на весь проект: ~2000 строк, из них ~650 перенос. Чистое ядро покрыто тестами хорошо:
около 400 тестов без GUI против 239 в `test_gui_smoke.py` (`test_core`, `test_publish`, `test_templates`, `test_localrepo`,
`test_notifier`, `test_real_svn` на настоящем `svnserve`, фейк `tests/fake_svn.py` с режимами auth/authz/noconn/hang).
Для CLI тесты пишутся на этом же фейке.

## 2. CLI

### 2.1 Форма и сборка

Консольный `svnlite.exe` (имя для агента), отдельная точка входа `svnlite_cli.py`, отдельный `packaging/svnlite-cli.spec`
с `console=True`, `excludes=['tkinter']`, без UPX. Причины:

- Текущий `SVN-lite.exe` собран `console=False`: у такого exe нет консольного вывода, а `cmd` не ждёт GUI-процесс, так что код возврата
  теряется. Можно ли получить stdout у windowed-exe через унаследованные каналы, не проверено (проверять на месте).
- `main()` окна сразу берёт мьютекс единственного экземпляра и при любых аргументах открывает окно, а `--tray` только один из ключей
  (`autostart.TRAY_ARG`). Смешивать режимы в одном exe значит маршрутизировать `argv` до импорта tkinter. Отдельный exe проще.
- Самообновление (`selfupdate.py`) подменяет только `SVN-lite.exe`. CLI-exe нужно добавить в `release.py` и в скрипт подмены,
  иначе версии разойдутся. Запущенный агентом `svnlite.exe` блокирует собственную подмену (скрипт ждёт до минуты).
- Одиночный exe PyInstaller при каждом запуске распаковывается во `%TEMP%` (порядка 1-3 с и проверка антивирусом). Для CLI вызова
  это терпимо, для частых вызовов агента лучше onedir-сборка или долгоживущий MCP.
- Для администратора и разработки: `python -m svnhelper.cli` (Python на ПК сотрудников не нужен).

CLI не берёт мьютекс окна, не создаёт трей, не пишет в реестр, не вызывает `setup_logging()` (ротация общего файла
двумя процессами на Windows падает с `PermissionError`): журнал `svn_helper_cli.log` рядом.

### 2.2 Команды

Адресация проекта: имя из списка `projects` (без регистра) или полный путь; чужие пути не принимаются (раздел 3.3). Допускать форму
`/c/Users/...` (Git Bash, который использует Claude Code на Windows, часто подставляет её агенту).

Только чтение (по умолчанию `--format json`, для человека `--format text`):

| Команда | Что делает | Сеть |
|---|---|---|
| `doctor` | svn найден? версия, откуда конфиг (рядом / общий / кэш), сервер, вход есть?, режим политики | да, лёгкий листинг |
| `projects [--dir D]` | проекты в папках для проектов (`settings.project_dirs`, `work_dir`): имя, путь, тип, линия, номер | нет |
| `status [проект ...\|--all] [--offline]` | состояние: актуален / есть новое / правки / то и другое / конфликт / повреждена / обычная папка / версия; число правок и нового; занятые вами | `status -u`, `--offline` без сети |
| `changes <проект>` | мои несохранённые файлы (вид, нужно ли занимать, занят ли мной) | нет |
| `incoming <проект>` | что нового на сервере: кто, когда, комментарий, файлы | да |
| `history <проект> [--limit 20]` | последние сохранения | да |
| `locks <проект>` | мои и чужие занятые файлы с давностью | да |
| `templates` | шаблоны (из кэша, если нет связи) | да/нет |

С побочными эффектами (все по умолчанию запрещены политикой, раздел 3.3):

| Команда | Что делает | Защита |
|---|---|---|
| `get-new <проект>` | получить новое | нет конфликтов автоматически: `conflicts` в ответе; не трогает папку, занятую другим процессом |
| `save <проект> --message-file F\|- [--files ...]` | сохранить на сервер | двухшаговая: без `--confirm` только план и токен (список файлов, комментарий, проверки), с `--confirm ТОКЕН` выполнить |
| `lock <проект> <файл>...`, `unlock ...` | занять / освободить | только свои; чужое не ломается (`--force` не существует) |
| `new-project --template T --field name=... [--storage local]` | проект из шаблона | по умолчанию только на этом компьютере; на сервер отдельным разрешением |
| `publish <папка> --place ...` | отправить на сервер | отдельное разрешение, двухшаговая |

Не делать никогда: `resolve`, `cleanup`, `revert`, `switch`, удаление на сервере, `--force`, смену настроек.

### 2.3 Вывод и коды возврата

Единая обёртка, `ensure_ascii=False`, `sys.stdout.reconfigure(encoding="utf-8")` в JSON-режиме (в текстовом режиме кодировка консоли,
`errors="replace"`):

```json
{"ok": false, "command": "status", "data": {...},
 "error": {"kind": "no_connection", "message": "Нет связи с сервером, проверьте сеть или VPN.",
           "svn_codes": ["E170013"]},
 "warnings": ["Проверка пропущена: проект занят другим процессом"]}
```

Поля `state`, `kind` и ключи JSON стабильные, английские (для агента). Тексты `message`/`next_step` по-русски, словами
сотрудника и из тех же `messages.*`, чтобы работал автотест слов svn (`tests/test_ui_texts.py` расширить на тексты CLI).
Технические детали (номер версии, адрес, коды `E######`, «сырой» ответ svn после `messages.redact`) только в блоке `svn` и при `--details`.

Коды возврата, по `ErrorKind` из `svn_core`:

| Код | Смысл |
|---|---|
| 0 | успех |
| 1 | прочая ошибка (`OTHER`, `BUSY`, неожиданное) |
| 2 | неверные аргументы (argparse) |
| 3 | нет связи / сервер не отвечает (`NO_CONNECTION`, `TIMEOUT`) |
| 4 | нужен вход (`AUTH`) |
| 5 | нет прав (`AUTHZ`, `READ_ONLY_LINE`, `LOCKED` чужим) |
| 6 | отказ политики: режим только чтение, папка не разрешена, лимит, нет подтверждения |
| 7 | нужна работа человека: конфликт, «на сервере новее» (`OUT_OF_DATE`), файл надо занять (`LOCK_REQUIRED`) |
| 8 | папка занята другим процессом (окно, другой запуск) |
| 9 | svn.exe не найден |

### 2.4 Вход на сервер

Пароль агенту не нужен и в CLI не хранится:

- По умолчанию CLI создаёт `SvnClient` без учётных данных. Клиент запускает svn с `--non-interactive`, `stdin=DEVNULL`, то есть svn берёт
  пароль из своего кэша (`%APPDATA%\Subversion\auth`, общий с TortoiseSVN). Он есть, если сотрудник входил в окне с галочкой «Запомнить пароль»
  (по умолчанию включена). Иначе `AUTH` -> код 4, текст: «Откройте SVN-lite и войдите: кнопка «Сменить пользователя…»».
- Опция `--use-saved-login` (выключена; включается только в файле политики человеком) читает DPAPI-пароль через
  `config.effective_credentials`. Пароль идёт в svn через stdin, наружу не печатается; в ответ и журнал только `Credentials.__repr__` с `***`.
  В первом этапе не делать.
- В команде и ответе пароль/логин в аргументах не принимаются. Имя пользователя берётся из настроек, выводится только в `doctor`.
- Оговорка: любой процесс того же пользователя технически может прочитать DPAPI-значение в `settings.json` или пароль из `svn_helper.json`
  рядом с exe. От агента с доступом к файлам защищают правила `permissions.deny` для чтения этих путей (раздел 4), а не код CLI.

## 3. MCP-сервер

### 3.1 Как устроен

Python SDK `mcp` (stdio), запуск `svnlite.exe mcp` (или отдельный `svnlite-mcp.exe`). По свежей документации (Context7):
в версиях 1.x класс `mcp.server.fastmcp.FastMCP`, в 2.x он переименован в `mcp.server.MCPServer`; `ToolAnnotations(read_only_hint=...,
destructive_hint=..., idempotent_hint=..., open_world_hint=...)` есть в обеих; аннотации лишь подсказки клиенту, не защита. Версию в `requirements`
закрепить (например, `mcp>=1.x,<2`) и перед стартом проверить актуальный синтаксис на установленной версии.

Практические особенности:

- stdout это канал протокола: никаких `print` и логирования в stdout. Ядро пишет только в логгер; svn запускается со `stdin=DEVNULL`
  (иначе svn мог бы съесть байты протокола), что `SvnClient._popen` и делает, если нет пароля.
- `SvnClient` блокирующий: tools вызывать через `anyio.to_thread.run_sync` (или `asyncio.to_thread`), для долгих операций слать
  `ctx.report_progress`. Таймаут вызова инструмента у клиента ограничен (в Claude Code настраивается переменными окружения): `get-new`
  большого проекта и `publish` могут не уложиться, для них нужна схема «запустить -> `job_status`» (второй этап MCP).
- Короткий кэш состояния проекта (например, 60 с), чтобы агент в цикле не нагружал сервер запросами `status -u`.
- Зависимости: `mcp` тянет pydantic, anyio, httpx, starlette, uvicorn и др. (на Windows также pywin32; по памяти, проверить). Для
  exe это десятки мегабайт и новые скрытые импорты PyInstaller, поэтому mcp только в отдельном exe, не в `SVN-lite.exe` и не в
  лёгком `svnlite.exe`.
- Подключение: `claude mcp add --scope user svnlite -- C:\...\svnlite.exe mcp` или `.mcp.json`. Для Claude Desktop запись в
  `claude_desktop_config.json`. Файлы настроек клиента правятся на каждом ПК: нужен пункт в окне «Справка -> ИИ-помощник»,
  который покажет готовую команду и скопирует skill (этап 7).

### 3.2 Какие tools и resources

Для всего, что агент должен уметь «вызвать сам», использовать tools (resources клиенты показывают человеку, модель редко читает их сама).
Resources сделать необязательным дополнением: `svnlite://projects`, `svnlite://project/{имя}/status`. Prompts по желанию:
готовый запрос «что изменилось в моих проектах».

| Tool | Аннотации | Подтверждение |
|---|---|---|
| `list_projects`, `project_status`, `project_changes`, `project_incoming`, `project_history`, `project_locks`, `list_templates`, `doctor` | `read_only_hint=True` | не нужно |
| `get_new` (получить новое) | read_only=False, destructive=False | запрос клиента; в политике `get_new` разрешён по умолчанию при `mode=write` |
| `save_project` (сохранить на сервер) | read_only=False, destructive=False, idempotent=False | двухшаговый: `save_project(plan)` -> токен -> `save_project(confirm=токен)`; человек видит список файлов и комментарий |
| `lock_file`, `unlock_file` | read_only=False, destructive=False, idempotent=True | запрос клиента |
| `create_project_from_template` (локально) | read_only=False, destructive=False | запрос клиента; сервер только с отдельным разрешением |
| `publish_project` (отправить на сервер) | read_only=False | отдельное разрешение + токен |

Внутри tools вызываются те же функции `ops.*`, что и в CLI, а не подпроцесс CLI.

### 3.3 Защита от опасных действий агента

Первая линия защиты: клиент. Мутирующие tools не добавлять в `permissions.allow` Claude Code, тогда клиент спрашивает человека на каждый вызов
(в Claude Desktop похожая кнопка подтверждения). Elicitation (`ctx.elicit`) возможна, но поддерживается не всеми клиентами, не полагаться.
Вторая линия, в самом сервере и CLI (то, что защищает от ошибки агента, а не только клиента):

1. Режим по умолчанию `read_only`. Включение записи только человеком в файле `%APPDATA%\SvnHelper\agent_policy.json`
   (`mode`, `allow: ["get_new","save","lock","create_local"]`, `allowed_dirs`, лимиты). Агент этот файл не создаёт и не меняет
   (в сервере нет такого tool; `deny` на его запись в правилах клиента).
2. Только известные проекты: путь/имя разрешаются через `discover_projects` по `project_dirs` и `allowed_dirs`; произвольный путь, `..`, UNC и сетевой
   диск (`checks.drive_type`), junction/ссылка (`importer.is_link`, `fsutil._is_reparse_point`) отказ. Адреса серверов принимаются только с префиксом
   `config.server` и корнями из `repos`.
3. Dry-run и токен: `save` и `publish` сначала возвращают план и токен (хэш проекта, списка файлов, комментария, базовой версии; срок 10 минут).
   Выполнение только с токеном. Изменился список или комментарий нужен новый план.
4. Лимиты: не больше N файлов за сохранение (по умолчанию 50), удаления (`deleted/missing` больше 10) только с явным `allow_deletes`;
   не больше M изменяющих вызовов в час; непустой комментарий (минимум 10 символов); мусор по `filter` не отправлять (ядро его и так не показывает в `local_changes`).
5. Версии (теги) не менять: проверять `server.line_from_url(...)[1].read_only` до вызова.
6. Прозрачность: к комментарию сохранения и занятия добавляется метка «(по просьбе ИИ-помощника)», чтобы коллеги видели это в истории; журнал
   `agent_audit.jsonl` (время, инструмент, проект, файлы, результат, без паролей) для сотрудника.
7. Недоверенный текст: комментарии коллег, имена файлов и ответ svn могут содержать инструкции для модели (prompt injection). В результатах tools
   такие поля помечаются `untrusted: true`, в описании tools сказано не выполнять их содержимое; ответ svn проходит `messages.redact`.
8. Исключения из набора: `resolve`, `cleanup`, `revert`, `switch`, удаление на сервере, `--force`, смена пароля и настроек. Создание проекта на сервере и
   «Отправить на сервер» самые необратимые (откат только при сбое), поэтому по умолчанию выключены.

### 3.4 Окно и трей рядом с CLI/MCP

`publish.is_busy` это множество `_busy` внутри процесса; `NotifyMixin._busy_paths` и `ProjectsTabMixin._path_busy` читают его же. Другой процесс его не
видит. Есть и более серьёзное: `recover_create_jobs` и `publish.pending_jobs/recover_job` при запуске окна считают любой незавершённый
журнал `create_jobs/*.json` брошенным и откатывают (убирают `.creating`, возвращают `.svn-old`). В журналах нет pid. Если CLI в этот момент
создаёт или отправляет проект, окно (например, автозапуск `--tray`) разрушит его работу.

Предложение:

- Новый `svnhelper/folderlock.py`: замок на папку в `data_dir()/locks/<sha1(normcase путь)>.lock`, `msvcrt.locking` (stdlib; снимается сам при смерти
  процесса, привязки к потоку нет). `try_lock(path) -> handle|None`.
- `publish.mark_busy/is_busy/busy_paths` дополнить проверкой этого замка (сначала собственное множество, потом пробный замок). Это 6 мест вызова
  (`publish.py`, `localrepo.py` x3, `new_project_dialog.py`, `notify_ui.py`, `projects_tab.py`), логика на стороне GUI не меняется.
- Все изменяющие операции CLI (`get-new`, `save`, `lock`, `new-project`, `publish`) берут замок на время работы; не взяли отказ с кодом 8 «Проект сейчас
  обрабатывает другая программа». Читающие операции замок не берут; если папка занята, сообщают в `warnings`.
- В журнал задач записывать `pid` и время старта процесса; разбор при запуске окна пропускает журналы живых процессов.
- Окно обновляет состояние строк раз в несколько секунд и проверку сервера не чаще раза в 5 минут (`AUTO_CHECK_SEC`), поэтому после
  сохранения из CLI оно может до 5 минут показывать старые «правки». Это неудобство, а не порча данных (повторное сохранение даст «сохранять нечего»).
  Позже можно сделать общий файл событий или вызов `tray.notify_running_instance`.

### 3.5 Тексты для агента и для сотрудника

Агент знает svn, но отвечать сотруднику он должен его словами (`PLAN_v3_ui.md`: без commit, update, revision, lock). Поэтому:
в JSON всегда два уровня: стабильные коды (`state`, `kind`) и готовый русский `message`/`next_step` из `messages.*` (слова интерфейса:
«сохранить на сервер», «получить новое», «занять файл», «сохранение № N»). Технические детали отдельно, по запросу. В skill/описании tools
написан короткий словарь: что агент говорит человеку («сохранил на сервер, сохранение № 7»), а не «commit r7».

## 4. Альтернатива и дополнение: `.claude/` без MCP

Для Claude Code достаточно CLI + skill, MCP не обязателен.

- Пользовательский skill `%USERPROFILE%\.claude\skills\svn-lite\SKILL.md`: когда применять («что с моими проектами», «что нового»,
  «сохрани на сервер»), какие команды `svnlite ... --format json`, словарь терминов, правило «сначала план, потом подтверждение пользователя», что делать
  при кодах 3/4/7/8. Frontmatter `allowed-tools: Bash(svnlite:*)`.
- Slash-команды `/svn-status`, `/svn-save` (шаблоны в `commands/`).
- Права в `settings.json`: `allow` для `Bash(svnlite status:*)`, `changes`, `incoming`, `history`, `locks`; `ask` для `save`, `get-new`, `lock`, `unlock`, `new-project`;
  `deny` для `Bash(svn:*)`, `Bash(svn.exe:*)`, `Bash(svnadmin:*)` и `Read`/`Edit` на `%APPDATA%\SvnHelper\settings.json`, `svn_helper.json`,
  `agent_policy.json`, `%APPDATA%\Subversion\auth`. Это единственная защита от обхода CLI через сырой `svn`.
- Hook `SessionStart`: запускает `svnlite status --all --offline` и добавляет в контекст «у вас 2 проекта с несохранёнными правками». Hook `PreToolUse`
  по `Bash`: блокирует прямой `svn commit/update/lock` с подсказкой использовать `svnlite`.
- Важное: не класть `.claude/` внутрь рабочих копий проектов (папка попадёт в SVN-проект и «Новое» у коллег). Только пользовательский уровень или плагин.

Когда MCP оправдан:

1. Пользователи работают не в Claude Code, а в Claude Desktop или другом клиенте без Bash. Для конструкторов это вероятный случай, предположение
   надо подтвердить. Тогда CLI они вызвать не могут, и MCP единственный путь.
2. Нужны типизированные схемы, подтверждения по каждому tool в интерфейсе клиента, прогресс и долгоживущий процесс (без распаковки exe на каждый вызов,
   с кэшем состояния).
3. Против MCP: лишняя зависимость и exe в десятки мегабайт, процесс со своим жизненным циклом, труднее отладка, версию клиента и SDK
   нужно держать в согласии. Поэтому архитектура: общий слой `ops`, CLI его первый потребитель, MCP второй.

## 5. Риски и ограничения

| Риск | Что происходит | Мера |
|---|---|---|
| Кодировки | svn выводит cp1251/cp866/UTF-8, ядро уже подбирает (`decode_output`: utf-8, ANSI, OEM); `--targets` пишется в ANSI, комментарий в UTF-8 (проверено в `commit`). Консоль `cmd` в 866/1251 | JSON только UTF-8; комментарий через `--message-file`/stdin, не через командную строку; не использовать `.bat`-обёртки; в тестах Кириллица в пути и комментарии |
| Пути | кириллица, пробелы, `@` (ядро добавляет `@`), длинные пути; Git Bash подставляет `/c/...` | нормализация `/c/..` в `C:\..`; адресация проекта по имени |
| Два процесса и `wc.db` | запись (update/commit/lock) берёт блокировку копии; `E155004` классифицируется как `OTHER`, а окно на нём делает `cleanup` и повторяет: чужую рабочую блокировку этот `cleanup` снимет посреди работы CLI | межпроцессный замок (3.4) и в окне тоже перед `cleanup`; CLI сам `cleanup` не вызывает |
| `settings.json` | `SettingsStore.save` пишет весь файл из памяти окна: правка из CLI (`local_histories` при создании проекта с историей, `recent_comments`) будет затёрта, проект потеряет «архив» | CLI/MCP читают настройки и не пишут; при создании с историей перечитывать `local_histories` перед записью (`save` с слиянием) или не включать историю в CLI на первом этапе |
| Журналы задач | окно при старте откатывает чужие незавершённые задачи | `pid` в журнале (3.4) |
| Журнал `svn_helper.log` | ротация общего файла двумя процессами | отдельный файл CLI |
| Фоновая проверка окна | раз в 15 минут `status -u` по всем проектам, плюс запросы агента | кэш 60 с, лимит вызовов, `--offline` |
| Антивирус | консольный exe из PyInstaller (особенно с UPX) запускает `svn.exe` по просьбе процесса Claude/node; EDR может счесть подозрительным | `upx=False`, подпись exe, согласовать исключение с ИТ; проверить на целевом ПК |
| exe и `mcp` | рост размера, скрытые импорты, медленный старт | отдельный exe, `mcp` грузить лениво |
| Самообновление | запущенный агентом `svnlite.exe` блокирует подмену; версии CLI и окна расходятся | обновлять оба файла в `release.py` и в скрипте подмены, CLI показывает версию в `doctor` |
| Безопасность паролей | пароль в `svn_helper.json` рядом с exe открытым текстом; DPAPI читается любым процессом пользователя; кэш svn | CLI пароль не читает; `deny` на чтение файлов; `doctor` не печатает логин-пароль; тест: в stdout/журнале нет пароля |
| Prompt injection | комментарии и имена файлов приходят от коллег | `untrusted`, подтверждение человека, лимиты |
| Потеря данных | `update` при открытом Компасе/Word даёт `BUSY`; сохранение файла без занятия `LOCK_REQUIRED`; автоповторов у агента нет, возвращается код 7 | ядро уже классифицирует, CLI передаёт как есть |
| Не проверено | живой `svn://192.168.11.11`, собранный exe, окна TortoiseSVN (см. `TODO.md`) | включить в ручные проверки этапа 7 |

## 7. Открытые вопросы владельцу

1. Каким клиентом пользуются сотрудники: Claude Code (есть Bash) или Claude Desktop (только MCP)? Это решает, нужен ли MCP на первом этапе.
2. Нужно ли агенту сохранять и отправлять на сервер сразу, или на первом этапе достаточно просмотра и «получить новое»? Рекомендация: просмотр, затем сохранение с токеном.
3. Должен ли помощник видеть чужие проекты на сервере вне скачанных папок (листинг дерева `server.load_folder`)? В плане не включено.
4. Согласие с ИТ на второй exe и на метку «ИИ-помощник» в комментариях к сохранениям.
